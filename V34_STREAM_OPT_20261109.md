## Profile: what was expensive

The original graph **already computes only three temporal taps per block**; it has **zero Conv nodes** and does not recompute temporal windows. The cost was per-row tensor operations/history management, not a full convolution over a window.

## Execution changes, architecture unchanged

Same 46,274 parameters: 168→64 ReLU projection, eight 64-channel residual depthwise k3 blocks at dilations1/2/4/8/16/32/64/128, pointwise64×64 mixers, same activations/head and 511-row receptive field. Existing batched training remains untouched.

`v34_stream_ring.py` hand-builds a compact fp32 graph, with fixed three-tap multiplies/sums and pointwise Gemms. Reassociating pointwise bias with the residual permits Gemm+ReLU fusion; it changes fp32 rounding slightly, not the real-arithmetic network. Graph size192,636 bytes, versus original337,409 bytes.

Each block's input history is a **time-major circular buffer** of length2d, channels64. Total history stays **127.5 KiB**. A common phase modulo256 addresses all power-of-two buffers. **256 IOBindings are created once**, pointing directly at the two historical tap rows for every block. ORT computes the current tap and writes the eight block inputs into a preallocated **2-KiB scratch buffer**. Only after ORT finishes are these copied into their circular slots, preventing input/output aliasing. Previous prices have separate preallocated input/output arrays. All large state/input/output arrays are allocated at initialization; the API still returns a small copied two-float prediction. Binding metadata/startup memory is additional to the history buffers and has not been separately quantified.

A new sequence zeros circular history once, initializes previous prices from its first raw row (zero price differences), and resets the phase. Every warm-up row executes and updates state. There is **one ORT call per row**. Dynamic int8 is retained only as prior evidence; fp32 is the selected execution path because int8 was slower. No model retraining, architecture reduction or fallback architecture was necessary.

## Correctness and limitations

- Optimized streaming vs batched PyTorch: max output error **4.77e−7**, including 1,000-row boundaries and ring wraparound.
- Optimized vs original fp32 streaming: max **5.97e−7**.
- Whole vs 1,000-row batched chunks: exact on benchmark data.
- All eight circular histories vs batched block-input histories after wraparound: max **9.54e−7**.
- Future perturbation leaves previous outputs exactly unchanged; sequence reset agrees with a fresh adapter exactly; repeated sequences/repeats are bitwise deterministic; warm-up updates are verified.
- Tests use the existing **100-update smoke checkpoint**, two real sequences, not trained-model accuracy evaluation. New streaming callback and static bindings are prototypes, not a built submission. Longer real-data serving, deployment-platform speed, startup/binding memory and fully trained-weight numerical validation remain to be checked before deployment. No full training or submissions were launched.
