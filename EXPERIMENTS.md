# Experiment log (Team Varanasi)

One row per run. Add yours before you launch. Never reuse a `--name`.

## Team rules (shared `user_9` login, shared GPUs)

- One GPU each, and check `nvidia-smi` first. Suggested: GPU 0 = Lnv, GPU 1 = Mukesh, GPU 2 = Tejas, GPU 3 spare. Before Oct 19 the training scripts forced GPU 0 whatever you set, so `CUDA_VISIBLE_DEVICES` did nothing and two runs shared one GPU (about 3 steps/s each instead of about 19). Fixed in train_v1.py and train_v2m.py with `os.environ.setdefault`. After launching, check in `nvidia-smi` that the memory on YOUR GPU went up.
- Always launch in the background so closing a tab cannot kill the run:
  `CUDA_VISIBLE_DEVICES=1 nohup python train_v1.py --hidden 128 --epochs 5 --n-val 1873 --n-holdout 300 --eval-every 12800 --seed 0 --name train_vN > ~/work/train_vN.nohup.out 2>&1 &`
- Do not type in a terminal tab where someone else's job is printing. Ctrl+C kills it.
- Tell the group before using a leaderboard submission (5 per day for the whole team).
- Commit the code behind every result, by file name (never `git add .`). Keep seeds fixed. The top 8 must reproduce their result for prize verification.
- No weights, caches or zips in git. No passwords or tokens in any file.

## Lessons

- Shared-stream training (train_multi.py, Oct 20): one process trains K models (--models "name:seed:arch:aux:aux_weight,...") from one batch stream, so each batch is read from the HDD once. Each model has its own seed, optimizer, schedule, loss, log ~/work/{name}.log and {name}_best.pt / {name}_final.pt; eval reads each valid batch once for all K. Checks on GPU 1, all exact: K=1 reproduces train_v2m.py (no aux) and train_v5m.py (aux) smoke loss lines, eval and weights bitwise; two identical specs give identical lines and weights; a model's weights do not depend on which other models share the run. GPU compute is about 68 model-steps/s (GRU hidden 128, aux or not), and the models run one after another, so wall rates are about 68 / 33 / 24 steps/s for K = 1 / 2 / 3 with data from page cache (peak GPU memory 1.79 GB at K = 3). The disk feeds about 16 steps/s (103 MB per 20-step batch at about 82 MB/s), so up to K = 3 (and about K = 4) the GPU keeps up and every model trains at the disk-bound solo rate: a K = 3 run should take about the wall time of one run. Use it for seed or ablation sets instead of queueing runs.
- Training knobs (v14-v20, Oct 20): weight decay 0.05-0.1 (v7 used 0.01) was the only one that helped, about +0.003 on a single model (v18c 0.6857, v19a 0.6856). No gain from dropout (v16-v18), aux heads (v14), 3 layers (v16c), alpha 0.75 (v16b), an EMA of the weights (v20a: +0.009 early, 0 at the end of the cosine schedule), peak lr 2e-3 (v20b, -0.0016) or hidden 192 (v20c, -0.0012 and 6x slower to train). wd 0.3 is too strong. The recipe is at a ceiling near 0.686; further gains need a change in data, inputs or targets, not in the optimizer. Confirmed Oct 21 (v22-v24): Gaussian input noise 0.05 / 0.15 (-0.0010 / -0.0014), peak lr 5e-4 (-0.0018) and 7 epochs instead of 5 (wd 0.05 / 0.07 / 0.1: 0.6839 / 0.6849 / 0.6852) give no gain; a third data seed lands at 0.6849-0.6856 and pairs no better than v18c+v19a (ensemble_check10).

- Two training runs at once each drop to about 3 steps/s, even on separate GPUs (about 17 steps/s alone). Likely cause: the container's 30 GB memory limit includes page cache, so both runs stream their caches from disk and fight over it. A full valid pass (ensemble or scoring script) has the same effect on a running job. Run one training job at a time, or pause one with `kill -STOP <pid>` and resume it with `kill -CONT <pid>`.
- `ps -eo args` truncates long command lines in background scripts, so a grep for the run name can miss the process. Use `ps -ww -eo pid,args` or `pgrep -af <name>` to find processes.
